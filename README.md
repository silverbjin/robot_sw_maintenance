# 지속 가능한 로봇 운영을 위한 소프트웨어 유지보수 이해

**Understanding Software Maintenance for Sustainable Robot Operations**

> **플립 러닝(Flipped Learning) 학습 자료 저장소**  
> 사전 학습으로 개념과 절차를 이해하고, 수업에서는 실제 사례를 진단·판단·검증하며, 수업 후에는 근거(Evidence)와 결과를 기록합니다.

이 저장소는 한국기술교육대학교 온라인평생교육원의 동명 교육과정(총 **12회차**)을 위한 학습 자료와 실습 패키지입니다. 로봇 소프트웨어를 *설치하는 방법*뿐 아니라 **설치 가능 여부 판단 → 초기 설정 → 업그레이드/롤백 → 장애 진단 → 사용자 교육 → 유지보수 결과 관리**에 이르는 운영 관점의 판단 과정을 학습하도록 구성했습니다.

### 학습 목표

이 과정을 마치면 다음을 수행할 수 있습니다.

1. 로봇 소프트웨어를 설치하고 초기 운영 환경을 점검·설정한다.
2. 버전 및 변경 이력을 관리하고, 업그레이드·백업·롤백을 통해 안정적인 운영을 지원한다.
3. 사용자 교육과 유지보수 절차를 수행하고, 점검 결과 및 후속 조치를 문서화한다.

## 2. 플립 러닝 학습 방법

이 저장소는 **명령어를 그대로 복사해 실행하는 것**보다 *왜 점검하는지, 무엇을 정상으로 판정하는지, 다음에 어떤 조치를 할지* 설명할 수 있도록 설계되었습니다.

| 단계 | 학습자 활동 | 확인할 결과 |
| --- | --- | --- |
| **① 수업 전 · 사전 학습** | 해당 회차의 학습목표·개념을 확인하고 Lab 안내서/워크북을 읽습니다. 필요한 환경을 준비하고 궁금한 점을 적습니다. | 핵심 개념, 사전 점검, 질문 |
| **② 수업 중 · 적용과 판단** | 강사의 사례·시연을 관찰하거나 제공된 패키지로 실습합니다. 정상 기준과 현재 상태를 비교하고 원인·조치·복구 여부를 토의합니다. | 실행 기록, 비교 결과, 판단 근거 |
| **③ 수업 후 · 정리와 전이** | 결과 보고서·Evidence·체크리스트를 정리하고, 동일 절차를 다른 로봇 운영 상황에 어떻게 적용할지 정리합니다. | 제출물, 재검증 기록, 개선/후속 조치 |

**실습 공통 사고 절차**

```text
정상 기준 확인 → 현상 관찰 → 상태·로그·이력 확인
         → 원인 가설과 영향 범위 판단
         → 안전한 조치(Fix / Rollback / 보고) 선택
         → 동일 기준 재검증 → Evidence·이력 기록
```

> 강의계획서의 일부 회차는 **이론·사례 중심**으로 편성되어 있습니다. 해당 회차에 제공된 Lab 자료는 사례를 구체화하거나 수업 내용을 확장하는 보조 학습 자료이며, 모든 Lab이 실제 로봇을 사용하는 필수 실습이라는 뜻은 아닙니다.

## 4. Lab별 학습 안내 및 시작 자료

**Lab01 — 유지보수 개념과 장애 진단 사례**  
수명주기와 사후·예방 유지보수의 목적을 이해한 뒤, 보충 사례로 ROS 2 / Gazebo의 LiDAR 데이터 전달 장애를 살펴봅니다. *장애 관찰 → 센서/브리지 계층 분리 → 수정 → 재검증 → 기록*에 집중합니다.  
자료: [Lab01 소개](Lab01/README.md) · [LiDAR 사례 실습 가이드](Lab01/docs/03_SLIDE_LAB_GUIDE.md)

**Lab02 — 설치 전 환경 준비 상태 판정**  
개발 PC의 OS·아키텍처·메모리·디스크·네트워크를 확인하고, Loopback TCP 연결 및 장애 복구 후 **READY / NOT READY**를 판정합니다. 실제 로봇 없이 WSL 2 기반으로 진행할 수 있습니다.  
자료: [Lab02 소개](Lab02/README.md) · [학생 워크북](Lab02/student/04_student_workbook.md)

**Lab03 — ROS 2 Humble 설치와 검증**  
Ubuntu 22.04에서 ROS 2를 설치하고, 환경 변수·워크스페이스·Overlay·Talker/Listener까지 점검하여 **설치 완료와 실행 가능 상태의 차이**를 확인합니다.  
자료: [Lab03 소개](Lab03/README.md) · [설치 워크북](Lab03/student/03_student_workbook.md) · [검증 워크북(PDF)](Lab03/student/04_install_validation_workbook.pdf)

**Lab04 — 로봇 초기 설정과 안전한 동작 검증**  
myAGV 2023 Jetson Nano의 제어·센서·네트워크 구성을 이해하고, 저속 제어·센서·게이트웨이 동작을 단계적으로 점검합니다. 실제 장비의 동작 시험 및 장애 주입은 강사 통제하에 수행합니다.  
자료: [Lab04 소개](Lab04/README.md) · [학생 워크북(PDF)](Lab04/student/04_student_workbook.pdf)

**Lab05 — 업그레이드 이전 준비와 승인 판단**  
Git 기반 버전·변경 이력, 설치 환경, 변경 영향과 롤백 가능성을 살펴 **READY FOR UPGRADE / GO·NO-GO**를 판단합니다. 이 회차의 목표는 준비 상태 판정이며, 실제 업그레이드는 Lab06에서 다룹니다.  
자료: [Lab05 소개](Lab05/README.md) · [학생 워크북](Lab05/student/04_student_workbook.md)

**Lab06 — 애플리케이션 업그레이드와 롤백**  
제공된 ROS 2 애플리케이션의 변경 대상과 신규 모듈을 파악하고, 배포·백업·롤백을 수행하면서 이전 상태로 돌아갈 수 있는지 확인합니다.  
자료: [Lab06 소개](Lab06/README.md) · [학생 워크북(PDF)](Lab06/student/01_student_workbook.pdf)

**Lab07 — 업그레이드 후 장애 검증과 조치 선택**  
Mock LiDAR 시나리오를 이용해 Publisher/Subscriber 토픽 불일치를 재현합니다. ROS 2 상태와 Git 차이를 비교해 원인을 좁힌 뒤 **Fix 또는 Rollback**을 결정하고 같은 기준으로 재검증합니다.  
자료: [Lab07 소개](Lab07/README.md) · [학생 워크북(PDF)](Lab07/docs/01_student_workbook.pdf)

**Lab08 — 사용자 교육 자료와 절차 설계**  
사용자 역할과 수준을 구분하여 수행 중심 목표, 빠른 사용 안내서(Quick Guide), 정상/이상 판단 기준 및 장애 보고 방식을 설계합니다. 소스 수정이 아니라 **운영자 관점의 교육 설계**가 핵심입니다.  
자료: [Lab08 학생 안내](Lab08/Lab08_User_Training_Design_Student/STUDENT_README.md) · [학생 워크북(PDF)](Lab08/Lab08_User_Training_Design_Student/student/01_student_workbook.pdf)

**Lab09 — 사용자 FAQ와 문제 대응**  
사용자가 허용된 범위에서 로봇의 상태를 확인하고, FAQ에 따라 조치를 선택합니다. 해결되지 않는 문제는 임의로 시스템을 변경하지 않고 Evidence와 함께 보고합니다.  
자료: [Lab09 소개](Lab09/README.md) · [학생 워크북(PDF)](Lab09/workbook/01_student_workbook.pdf) · [FAQ](Lab09/workbook/02_faq.md)

**Lab10 — 피드백 분석과 교육 개선**  
사용자 행동 기록과 Evidence에서 사실을 추출하고, 문제를 분류한 뒤 매뉴얼·교육 개선안을 작성합니다. 개선 후에는 동일한 수행 기준으로 효과를 재평가합니다.  
자료: [Lab10 소개](Lab10/README.md) · [학생 워크북(PDF)](Lab10/student/workbook/Lab10_workbook.pdf)

## 5. 실습 환경 및 준비

| 구분 | 권장 구성 및 유의사항 |
| --- | --- |
| 기본 실습 PC | **Ubuntu 22.04 LTS + ROS 2 Humble**. Windows 11에서는 WSL 2 기반 Ubuntu 환경을 사용하는 회차가 있습니다. |
| 개발·운영 도구 | Git, Visual Studio Code, ROS 2 CLI, `colcon` 등. 필요 도구는 각 Lab의 지침을 우선합니다. |
| 시뮬레이션 | 일부 회차에서 Gazebo Fortress, Mock 센서 또는 교육용 데모를 사용합니다. |
| Lab01 별도 환경 | Windows 11 + Docker Desktop(WSL 2 backend), 컨테이너의 Ubuntu 22.04 / ROS 2 Humble / Gazebo Fortress 및 noVNC를 사용합니다. |
| 실제 로봇 | 일부 사례에서 **myAGV 2023 Jetson Nano**와 네트워크 장비를 사용합니다. 실물 장비 없이 진행할 수 있는 Lab도 있습니다. |

**중요한 호환성·안전 안내**

- 개발 PC의 **ROS 2 Humble / Ubuntu 22.04**와 특정 myAGV Jetson Nano의 **ROS 2 Galactic / Ubuntu 20.04**는 서로 다른 환경일 수 있습니다. 같은 ROS 2 버전이라고 가정하거나 DDS 직접 통신을 성공 조건으로 삼지 마세요. 해당 Lab의 게이트웨이·브리지·로컬 실행 안내를 따르세요.
- 실제 로봇의 주행, 센서 설정 변경, 장애 주입, 복구·재시작은 **안전 정지 및 강사의 감독** 아래 수행합니다. 교육용 Mock 데모의 안전성을 실물 로봇에 그대로 적용하지 않습니다.
- 모든 Lab이 동일한 실행 환경을 요구하지 않습니다. 명령을 실행하기 전에 **각 Lab의 README와 학생 워크북**을 먼저 확인하세요.

## 6. 저장소 사용 방법

```bash
git clone https://github.com/silverbjin/robot_sw_maintenance.git
cd robot_sw_maintenance

# 예: Lab02 학습 자료 확인
cd Lab02
```

1. 위 **전체 학습 구성**에서 학습할 회차의 `LabXX` 폴더를 엽니다.
2. 해당 Lab의 `README.md` 또는 연결된 **학생 시작 자료**를 확인합니다.
3. 수업 전 준비를 마친 뒤 강사의 안내에 따라 시연·사례 분석·실습을 진행합니다.
4. 워크북의 관찰 결과와 판단 근거를 기록하고, 해당 Lab에서 요구하는 보고서와 Evidence를 정리합니다.

### Evidence와 결과 기록 원칙

- **관찰 사실**과 **원인 가설**을 구별합니다.
- 명령 실행 성공만으로 복구를 단정하지 않고, **실제 데이터·기능·안전 상태**를 확인합니다.
- 변경 전/후 결과는 **동일한 기준**으로 비교합니다.
- 결과 보고서에는 **현상 → 점검 근거 → 원인 판단 → 조치 → 재검증 → 후속 조치**를 남깁니다.
- 민감한 IP, 계정, 비밀번호, 장비 식별 정보나 내부 로그를 공개 GitHub에 업로드하지 않습니다.
- Lab 폴더에 포함된 `student/`·`docs/`·`scripts/`·`reports/`·`evidence/` 등의 실제 구성은 회차마다 다를 수 있습니다.
